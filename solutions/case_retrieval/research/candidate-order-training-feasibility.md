# 训练候选顺序增强：CPU可行性，尚未训练

当前固定逆序推断并集在F1/F0及原dev取得正增量，但同模型逆序单独不优于原顺序。新假设是通过训练时保持标签语义的候选重排，降低顺序敏感性；这不能从已有集成收益直接推断为训练收益。既有JSON value2、public212扩池和额外ICL均已实际负结案，本次不复用它们当新方案。

严格train32旧124提示、880概念、2506患者对（594正）和原证据上下文不变。只逆序候选，并按相同可逆映射重编号prompt的顶层CID及目标JSON键；患者列表及顺序原留。124条prompt和答案双逆全对象/字节精确，119行候选变化、109行目标变化；训练派生候选链F3→F2/F2→F3，排除F1及outer0。没有读取新验证gold。

CPU实际2.835秒；复用冻结tokenizer JSON/Jinja及原encode函数，全部124原行的token、prefix/label SHA与旧真实TF5.20.2 tokenizer审计精确一致。原/逆各402594/402596 token，最大均5523，监督token均7170；无截断。当前本地tokenizers版本与远端不同，精确旧审计匹配是依据，不冒称依赖版本相同。

拟议等预算控制明确使用**四个124样本的逻辑epoch**：

| 项目 | 原顺序控制 | 顺序增强 |
|---|---|---|
| 四轮输入 | O/O/O/O | O/R/O/R |
| 每轮sample ID顺序、seed | 相同，20261023 | 相同，20261023 |
| 梯度累积 | 每组8，124末尾4单独flush | 完全相同 |
| optimizer calls / 样本曝光 | 64 / 496 | 64 / 496 |
| 总token / 监督token | 1610376 / 28680 | 1610380 / 28680 |
| 拟议warmup / peak LR | 4 calls / 1e-4 | 相同 |

普通248条直接两epoch只有62 calls，不能称为相同64；这里使用明确的四逻辑epoch，保持各调用sample ID与学习率时序相同。该四轮控制也不能直接当作旧两轮32calls的单变量比较。原模型加载、因果loss、LoRA与分组语义需在将来的实际入口复用，当前没有实现或运行新的训练循环。

按同A800旧124×2、full265×2、public212×2三个实际终点作token线性代理，每臂约2229–2299秒，两臂合计约74–77分钟；含旧加载/保存开销，非新实测或时间保证。未使用A100加权训练时间冒充同机同目标吞吐。若FLA取得真实数值/速度证据，再另估实际训练预算；当前不改变runtime。

当前只保留CPU准备，不启动GPU、fit、F1评分或原dev。源码/固定计划/摘要/精确64调用表见[小证据目录](../candidate_order_training_feasibility/source-manifest.json)。1.73MB逆序训练行、3.45MB拼接行、逐行token审计和模型资源留仓库外，manifest记录SHA及位置。
