# 接手审查：PatientPheX 仓库是否值得继续沿用

审查日期：2026-10-23。被审查代码基于提交 `919d7a2`。本次进行了源码审查、CPU 重跑、输出核验、关系样本重建及规则消融；未进行 GPU 训练或平台提交。

**结论：建议重建评测、验证和主方案；保留数据、历史输出及 CPU 词典版作为对照。** 当前仓库具有可运行的基线价值，但不足以作为可信的竞赛研发基础。继续在 v10 上逐条添加缩写和黑名单，不是推荐的主投入方向。现有实验也没有充分证据证明 NER 或关系模型路线不可行。

## 1. 比赛到底要求什么

输入是一篇可能包含多个患者、家系成员及一般疾病讨论的英文医学全文，另给定目标患者及其部分指称。系统需要：

1. 找到表型实体的精确字符边界，并映射到指定版本的 HPO 概念。
2. 判断每个表型属于哪个指定患者，输出每位患者的表型集合。一般疾病描述、其他患者的症状和否定症状需要区分。

例如“患者 A 有白内障，其妹妹没有白内障”，不能把段落中出现的白内障同时分给两个人。即使实体位置找对，HPO 链接错误也会影响官方成绩。

官方总分由实体提及 F1、文档概念集合 F1、患者关联 micro-F1、患者关联 macro-F1 四项等权组成。模型不超过 10B，HPO 固定为 2026-06-23 版的 HP:0000118 分支，不允许使用外部人工标注表型数据集。完整规则及榜单已保存在[比赛资料](competition/README.md)。

查询时已经进入赛后评测；正式 B 榜第一名为 0.738920，官方 Baseline 为 0.655178。**本仓库没有可核验的提交记录把某个输出文件对应到官方得分，因此不能给它估一个 B 榜名次，也不能用训练集分数与榜单比较。**

## 2. 现有方案实际做了什么

当前可直接运行的是 [src/local_predict.py](../src/local_predict.py)：

```text
增强词典 → AC 字符串匹配 → 缩写覆盖与黑名单 → 简单否定过滤
        → 输出全部命中实体及候选 HPO
        → 将同一 full_text 段落中的所有表型分给该段提到的所有患者
```

这里的“同 section”实际是同一个 `full_text` 列表元素，即同一 passage。没有完整的实体候选消歧、患者共指或跨段归属模块。`--self` 参数传入后没有参与计算，不会产生验证划分。

此前的 v3–v8 尝试了 PubMedBERT 关系二分类、BIO NER 与词典并集等方法；但模型文件、完整训练链路与日志未归档，当前无法复现其历史成绩。

## 3. 已确认的关键问题

### 3.1 评测器不能承担选方案的职责

证据：[src/evaluate.py](../src/evaluate.py) 第 12、22、43、65、85 行；[诊断结果](review/2026-10-23/evaluation_results.json)。

- 实体只比较 `offset/length`，完全忽略 HPO ID。
- `docF1` 计算逐文档的跨度 F1 平均，还会跳过空预测文档；官方是逐文档 HPO 集合统计后全局计算 F1。
- `zip` 按行配对，不校验文献 ID 或文件行数，尾部漏文档也能被忽略。
- 没有否定和复合实体处理；金标、预测均为空的患者在本地得到 F1=0，官方要求为 1。

已通过原函数运行极小反例：

| 输入变化 | 本地返回 | 问题 |
|---|---|---|
| 保持跨度、把所有 HPO 改错 | menF1=1，docF1=1 | 无法发现实体标准化错误 |
| 两篇文档，一篇全部漏预测 | docF1=1 | 空预测文档被排除 |
| 两篇金标，只交第一篇正确预测 | menF1=1，docF1=1 | 缺失尾部文档被 `zip` 忽略 |
| 文献 ID 全改错，保持相同跨度 | menF1=1，docF1=1 | 未校验文献配对 |

这不意味着所有本地分都单向虚高，而是指标定义不一致。按公开规则做近似诊断时，docF1 反而会升高；因此不能用一个固定折扣修正历史分数。

### 3.2 验证设计不足以支持泛化结论

**词典与训练金标高度重合。** 增强词典相对原始词典新增 2,035 个 surface，全部都出现在训练实体的 `text.lower()` 中；其中 2,028 个 ID 集合也完全相同。训练共 2,821 种独特 surface，增强词典覆盖 2,663 种。见[词典重合统计](review/2026-10-23/dictionary_overlap.json)。

这证明了重合，并不能单凭静态文件确定构建历史；仓库也没有能重建该增强词典的完整过程。不过，**使用该词典在全部训练集上回测，不能得到独立验证结论**。从训练标注构建词典本身是合理方法，问题是验证时应仅使用训练折构建，不能让验证折标签进入词典。README 所称 UMLS 来源在现有构建脚本中未得到支持。

**关系模型按 pair 随机划分，发生文档级泄漏。** [v3_build_rel_data.py](../src/v3_build_rel_data.py) 第 107–113 行丢弃文档信息后随机切分。只修正临时运行的路径、沿用原代码和 seed=42 重建后：

| 项目 | 数量 |
|---|---:|
| patient–entity pair 总数 | 26,339 |
| 平衡后的训练样本 | 21,492 |
| 验证样本 | 2,633 |
| 验证集文档数 | 79 |
| 同时出现在训练集中的验证文档 | **79 / 79** |
| 验证输入与训练输入完全相同 | **255 / 2,633** |

见[重建统计](review/2026-10-23/relation_samples.json)。README 提到的“随机 split 有泄漏”有依据；但没有 group split 代码及日志来核验其 `0.86 → 0.32` 数值。

NER 训练脚本是在切 chunk 前按文档划分 60/20，这一点合理，不应与关系模型的划分问题混为一谈。

### 3.3 患者归属是核心短板

证据：[src/local_predict.py](../src/local_predict.py) 第 99–118 行；[规则审计](review/2026-10-23/rule_audit.json)。当前逻辑是同段患者与同段 HPO 的全量组合。

在已有 80 篇训练集上，按每患者表型集合比较：

| 项目 | 结果 |
|---|---:|
| 预测患者–表型关系 | 3,331 |
| 正确关系 TP | 1,752 |
| 错误关系 FP | **1,579** |
| 漏掉关系 FN | 378 |
| Precision / Recall / micro-F1 | **0.5260 / 0.8225 / 0.6416** |

- 1,579 条错误关系中，997 条只来源于含多个指定患者的段落；40 条同时有单患者和多患者段落来源。这是归属规则易混人的直接证据，但这些错误也可能同时受实体误识别影响。
- 378 条漏关系中，270 条的 HPO 已在文档中抽到，但该患者没有与之同段的给定 mention；仅增加实体召回不能解决这些错误。
- 12 位金标表型集合为空的患者中，9 位被分配了错误概念。
- 43 条用原文表示的无 HPO 金标关系全部遗漏；现有规则只输出 `HP:` 开头的关联。

这些是训练集回看结果，不能外推成 B 集表现；即便在这种有利的回测条件下，患者归属仍有明显问题。

### 3.4 实体规则存在具体、可复现的缺陷

证据：[src/local_predict.py](../src/local_predict.py) 第 18–33、43–46、58–70、85–87 行；[缩写审计](review/2026-10-23/abbreviations.json)与[消融结果](review/2026-10-23/rule_ablations.json)。

- **长词没有完整词边界。** 只有长度不超过 4 的字母词检查边界，导致 `apoptosis` 中命中 `ptosis`、`intracranial` 中命中 `acrania`。训练集有 954 个词内部命中，其中 944 个不符合金标跨度与 ID。
- **v10 新增的七个缩写实际全部无效。** `sp/mr/mh/oa/rp/rd/di` 被加入自动机，但生成实体时 `len(stext)<3` 又将它们全部丢弃。移除这七项的消融输出计数与原版完全相同。16 个缩写条目共有 11 个受此限制。
- **部分缩写强制覆盖为错误概念。** 例如 `asd` 将词典原有 `HP:0000729` 覆盖为 `HP:0000750`（言语和语言发育迟缓）；训练集中 8 个 ASD 金标都是前者。本地跨度评测无法发现这个 ID 错误。
- **否定只是前 30 字符的子串检查。** 会把前句的 `no`、其他概念的 `negative` 影响到当前肯定症状；也未解决作用域问题。训练输出在 60 个金标否定跨度上仍预测了普通实体。
- **候选歧义和真实复合表型未区分。** 将一个词条的全部 HPO 候选以分号输出；官方会逐个计分，不能把多候选当成不会付出代价的召回策略。
- **嵌套命中未做边界选择。** 同时输出长短多个嵌套 span，形成大量边界错误。

为判断这些问题是否实际影响输出，进行了训练集内的单因素消融。下表使用“去除 NO、分号拆分、严格 `(offset,length,ID)` 集合匹配”的诊断口径，`-1` 也按普通字符串严格匹配；与官方对 `-1` 的说明有差异，不能称为官方分：

| 临时变体 | 实体 TP | 实体 FP | 实体 FN |
|---|---:|---:|---:|
| 当前规则 | 5,653 | 3,336 | 281 |
| 所有命中都检查左右字母边界 | 5,643 | **2,392** | 291 |
| 去掉被更长命中完全包含的短 span | 5,547 | **1,156** | 387 |
| 允许双字母实体输出 | 5,675 | 3,491 | 259 |

这些实验说明现有规则仍有明显实现问题。它们没有经过独立验证，不能直接将某一行当作新方案；尤其不能只解除双字母限制而不做缩写消歧。

### 3.5 旧模型失败不能代表技术路线失败

关系训练存在标签与输入问题：

- [v3_build_rel_data.py](../src/v3_build_rel_data.py) 第 86–104 行使用第一个重叠金标实体的 HPO 打正标签，而非验证待输出的词典候选。7,954 个正样本中，1,160 个的候选 HPO 与患者金标完全不相交。
- 输入只包含患者第一次 mention 的文本和局部候选上下文，没有患者 ID、位置或完整患者上下文；存在 117 种完全相同输入同时拥有正负标签，共涉及 392 条样本。
- `get_sentence` 向左遇到空格便停止，`Patient 2 had severe fever and cough.` 的上下文会变成 `fever and cough`，丢掉归属依据。

NER 链路也未完成可靠的端到端验证：

- [v5_train_ner.py](../src/v5_train_ner.py) 第 150–162 行仅用 `B-PHEN` 起点标签 F1 选模，没有评价实体终点和完整 span。
- [v5_predict_ner_union.py](../src/v5_predict_ner_union.py) 第 79 行使用末尾特殊 token 的 `(0,0)` 关闭实体。stub 调用原函数时，`with fever` 的实体应为 `(5,10)`，实际为 `(5,0)`，后续被静默过滤；v6 同样存在。
- 无词典映射的 NER span 一律设为 `-1`，后续关联又只接受 `HP:`。B v5/v6 的 11,604 个实体中，4,105 个（35.4%）是 `-1`；这不等于这些实体真实没有 HPO 概念，而是系统未完成标准化。
- 关系回填只按实体起点查找并取第一个，不校验长度。B v5 中有 886 组同起点多实体，其中 75 组第一个是 `-1`，后续却有有效 HPO。

因此，README 中“证明规则优于模型”“80 篇小数据使 NER 失败”的解释需要重新验证。当前可以确认的是这些具体实现和验证方案有缺陷。

### 3.6 资源版本与工程链路不完整

- `data/hp.obo` 为 2026-09-01，官方要求 2026-06-23。
- 按当前本地本体检查、解析 `alt_id` 后，B v10 有 106 个 HP:0000118 分支外单元和 6 个废弃概念单元。该统计使用的是本地版本，不冒充官方版本的非法 ID 判定。
- 训练输出还出现了 `HP:000328` 这种六位数字的畸形 ID。
- 8 个脚本硬编码前人的 `/dataset/wanggenyi/patient_phex` 路径。
- 关系数据构建写 `data/rel2/`，训练固定读 `data/rel/`，两者均未归档；原训练输入路径也与仓库布局不一致。
- 词典脚本读根目录 `hp.obo`，输出普通映射 `hpo_dict_v2.json`；当前预测器却要求 `dict/hpo_dict_augmented.json` 的 `combined` 结构，构建链未闭合。
- 缺少基础模型和 checkpoint、依赖锁定、完整运行命令、固定划分、训练日志及官方提交记录。两次 Git 提交中，旧代码是整体导入，无法还原实验演进。
- `outputs/local_pro_v10.jsonl` 缺 14 位指定患者，另加 1 位未给定患者，且没有对应生成脚本，不宜继续直接使用。

## 4. 哪些部分确实有价值

**数据和基本读写是可用的。** train 80 篇、B 100 篇均可解析；11 份历史输出的文档齐全，实体跨度和原文逐项吻合，没有重复文档或重复实体。一般输出保留了给定患者，仅上述 `local_pro_v10` 存在患者覆盖异常。

**CPU 规则版确实可复现。** 本次以 Python 3.12.14、pyahocorasick 2.3.1 重跑：

| 数据 | 文档 | 实体 | 患者关联 |
|---|---:|---:|---:|
| Train | 80 | 8,712 | 3,331 |
| B | 100 | 6,838 | 2,317 |

实体结果和患者表型集合与归档一致；`set` 迭代导致关联列表顺序不同，因此是语义一致，不是文件字节一致。

原评测器的训练集结果复现为：

| menF1 | docF1 | micF1 | macF1 | Score |
|---:|---:|---:|---:|---:|
| 0.765859 | 0.766889 | 0.641641 | 0.569480 | 0.685967 |

这仅是旧脚本的训练集自检。另存的[公开规则近似诊断](review/2026-10-23/evaluation_results.json)在处理 NO、复合实体和空患者后，总分约 0.7186，但正文筛选与 `-1` 文档级处理存在未公开细节，重复 mention 的计数也列了敏感性结果。**两组分数都不是官方成绩或泛化估计。**

## 5. 推荐的接手方案

| 部分 | 建议 |
|---|---|
| Train/B 原始文件、历史预测、现有 Git 记录 | 保留，作为原始资料和对照 |
| `local_predict.py` 的 JSONL 读写、偏移映射、AC 检索思路 | 可复用；将当前版本冻结为旧基线 |
| 增强词典 | 作为待核对资料保留；验证时按训练折重新生成，补齐构建来源 |
| `evaluate.py` 和实验划分 | **重建**，优先级最高 |
| 当前患者关联、HPO 消歧和否定逻辑 | **重做核心方法** |
| v3–v8 模型脚本 | 保留作参考，重新实现可验证的训练与预测流程 |
| README 历史分数和技术结论 | 作为待核实记录，不能作为选路线的依据 |

建议顺序：

1. **建立可信评测。** 对齐官方公开定义，添加错 ID、缺文档、空患者、NO、复合实体等有区分力的验证；未公开细节单独记录。固定按 `pmc_id` 分组的验证集或交叉验证，所有训练派生词典仅从对应训练折建立。取得指定 HPO 版本并验证分支和 ID。
2. **建立干净、可复现的基线。** 参数化路径，补依赖和配置；修正边界和缩写问题；保存数据、模型、配置、输出与分数之间的对应关系。先在同一文档验证划分上比较，不能继续用全训练回测挑规则。
3. **重做两个核心模块。** Task 1 使用候选发现、HPO 检索与上下文消歧、否定和边界判断；Task 2 使用给定患者提及、共指及跨句跨段证据做归属，显式区分家庭成员和一般疾病讨论。可把参数不超过 10B 的模型（例如官方基线使用的 Qwen3-8B）列为候选，与规则及小模型进行受控比较，效果以验证结果决定。

“重做”的投入应优先放在评测和任务建模，而非重新抄一遍数据读写。当前材料足够支持这个判断，但不足以承诺重做后的官方分数。
