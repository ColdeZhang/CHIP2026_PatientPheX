## 从本项目的真实问题出发

本项目当前的主要风险是：评分口径不可信、训练和验证混杂、历史实验缺少版本关联、已有坑可能在新会话重复发生。目标是让每次投入产生可检验的进展，并让下一位执行者能迅速接手。文档和工具的价值，以是否支持这些目标判断。

因此当前采用：稳定规则放 AGENTS，当前状态放 WORKLOG，实验方法和结果放实验记录，可复用教训放 HANDOFF。原始数据、完整日志和模型不随摘要反复复制。

## 为什么先用简单文档和 manifest

当前单仓库、少量执行者，最缺的是可靠证据与一致习惯。引入实验追踪服务、对象存储或复杂流水线，本身不能修复错误指标和验证泄漏；当前用 Markdown、小型 JSON 及配置文件即可满足接手与复现需求。

当出现多个执行者频繁并发、参数扫描难以检索、跨机器大产物管理困难，或手工版本关联持续出错时，再评估 MLflow、DVC 或同类工具。采用工具时保留现有实验 ID 和证据关联，不为迁移工具重做已有实验。

## 记录投入如何与任务价值相称

- 普通文档修改：台账一条加实际校验结果即可。
- 小型修复：记录问题、变更、关键验证；只有涉及模型选择或指标变化时才建实验记录。
- 模型/规则比较：运行前定义假设和比较条件，运行后记录关键结果、成本、局限与决定。
- 重大失败或长期路线决定：增加原因、替代方案及防复发措施；原始证据用链接，不复制大段日志。
- 任何记录只写已发生的事实；历史补录显式标注补录，未测量的成本和未核实的分数不补造。

体积提示值（单文件约 1 MiB、一次新增产物约 10 MiB）用于触发检查，便于防止误加入权重或全量日志；不是不可调整的硬门槛，也不新增审批流程。已有受跟踪的比赛数据和历史证据保留。

用户另明确要求防止会话异常造成记录丢失：重要进展应及时 commit 并 push，长运行及交接前保留检查点，并核验远端。该规则直接来自用户要求，执行细节见 AGENTS 第 8 节；常规同步不重复询问。Git 备份与大型产物保存分别核验。

## 检查这些规则是否有效

新会话应能从 HANDOFF 和台账找到：目标是什么、现在到哪里、结果可信到什么程度、相关代码/产物在哪里、下一步怎么做，以及哪些坑需要避开。

实验记录应足以重建关键运行条件；大产物应可定位或明确可重建；失败应留下避免重复投入的结论。如果出现文档重复、记录负担超过收益或关键证据仍找不到，应调整规则和结构，而不是机械增加模板。
